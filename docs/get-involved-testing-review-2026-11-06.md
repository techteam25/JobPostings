## Verification performed and limits

- The signup page at `http://localhost:3000/sign-up` loaded. A headless Edge check reproduced the missing legal links and premature email error without writing database data.
- Frontend `bun run type-check` passed, with one existing TanStack Table compiler warning. Backend `bun run type-check` passed. Thirty focused registration, password-reset, and profile-completion unit tests passed. Passing tests do not cover the missing behavior above.
- Authenticated browser flows, Google OAuth, email delivery, and historical profile HTTP failures were not reproduced. They require an isolated migrated test database, provider/test email configuration, and captured response bodies and correlation IDs. The Playwright configuration currently hard-codes `/opt/homebrew/bin/bun dev`, which prevents its normal web-server setup on Windows; downloaded Playwright browsers are absent locally.
- The live MySQL database still has 30 schema tables but only the historical baseline migration ledger row, with two missing foreign keys and 17 missing indexes after an interrupted bridge. Finish the separate data-preserving baseline repair before any new Drizzle schema migration. Do not run a new migration directly against this partially migrated database or hand-edit its ledger.

## Implementation sequence

### 0. Establish a safe, reproducible test path

1. Complete the reviewed MySQL baseline/ledger repair on a clone and cut over only after data checks and a fresh backup. Provision and migrate `jobpostings_test` separately. Keep Drizzle `generate` and `migrate` manual as required by `backend/CLAUDE.md`.
2. Make `frontend/playwright.config.ts` use a portable `bun run dev` command or an environment override. Use installed browser channels on Windows where appropriate. Add seeded seeker and employer fixtures to the isolated test database, never the live database.
3. For each historical 400/500, capture the endpoint, sanitized request shape, response body/error code, correlation ID, backend stack, and background-job result. Preserve a minimal reproducible fixture. Treat the June upload report and October login report as separate incidents until traces show a shared cause.

### 1. Fix signup, verification, and employer identity (P0)

1. Publish reviewed Terms and Privacy content at stable public routes or link to the organization’s authoritative pages. Replace the signup spans with real anchors that open without checking or unchecking consent. Add a browser test for navigation, keyboard use, and checkbox independence.
2. Replace whole-form `onChange` email and confirm-password equality messages with field-aware validation: validate format/match on blur or after meaningful input, retain strict submit validation, and clear stale errors when corrected. Test typing, blur, invalid submit, and correction.
3. Align the signup screen with the actual email-verification policy. When verification is required, show a pending-verification path and reliable resend; when disabled, route to the proper onboarding destination. Handle Better Auth’s `{ error }` responses on resend and sign-in, and map the frontend’s `ApiError` consistently. Use a safe, useful message for repeat signup and unverified accounts. Ensure email delivery errors fail the queued job so retry/alerting works.
4. Set a valid Better Auth backend base URL in every environment, verify trusted frontend origins and registered Google callback URLs, and add a first-time Google employer flow. Recommended: pass the selected account type through Better Auth OAuth `additionalData`, validate it server-side during new-user creation, and set `intent` only for that new user; never overwrite intent for an existing account during sign-in or account linking. Verify this against the installed Better Auth version before rollout. See the [Better Auth OAuth state documentation](https://better-auth.com/docs/concepts/oauth) and [base URL option](https://better-auth.com/docs/reference/options#baseurl).
5. Keep the person-first account model. Change the selector copy to **“Hiring manager / organization representative”** and explain that an organization is created after personal signup. This is a copy change, not a change to permission ownership.

**Acceptance:** first-time seeker/employer email and Google signups land in the correct onboarding; existing Google employer sign-in keeps employer intent; duplicate/retry and verification failures show actionable non-generic messages; failed delivery is observable and retryable; legal links work without changing consent.

### 2. Fix profile save and upload contracts (P0)

1. Reproduce the bio+phone and phone-only saves with a known valid profile in the isolated database. Define a dedicated user-editable profile DTO shared in tests between frontend and backend. Normalize phone numbers with the selected country or E.164 instead of assuming `US`; count visible bio text after entity decoding. Make `validation.middleware.ts` pass parsed/transformed data to controllers, and allowlist editable fields so file metadata and storage URLs remain worker-owned.
2. Preserve structured backend validation errors in `ApiError` and map field errors inline. A valid two-sentence bio and valid phone must save without a file; a phone-only edit must also save. Invalid input must receive a precise 4xx response with a field reason, never a generic 500.
3. Validate `req.file` directly per upload endpoint before queueing: accepted MIME and extension, size, missing file, and file contents where relevant. Map Multer and queue failures to explicit 4xx/5xx codes; clean temporary files on all failure paths. Tighten upload tests to exact 400/413/415 or the chosen contract, plus a distinct queue-failure 503/500 case.
4. Return an accepted/processing state when BullMQ has only queued the file. Show final success after worker completion and refetch; show worker failure with retry. Keep optimistic image URLs alive until replacement or rollback. Test queue acceptance, worker success/failure, and a profile save immediately after upload failure.

**Acceptance:** valid resume and image uploads reach permanent storage; rejected type/size returns a useful 4xx; queue/storage failure is not called “uploaded successfully”; profile Save does not depend on file upload; no orphan temp files remain.

### 3. Fix qualifications and preferences (P1)

1. In Add Education, omit only untouched blank rows at submit; keep partially filled rows invalid and provide an obvious Remove/Cancel action. Use stable row keys when removing entries. Test one completed school plus one untouched row, a partial second row, and cancel.
2. Move the shared date popover outside the scrollable viewport while keeping it within the dialog focus boundary; set collision/placement behavior deliberately. Browser-test month/year navigation, days 22–31, click, keyboard, and a short viewport for both Education and Work Experience. Verify a draggable scrollbar, wheel/touch, and the existing scroll button.
3. Provide an explicit **Self-employed / independent contractor** entry path. A short-term UI choice can submit a visible “Self-employed” label to the current required company field. The durable model should store employment kind separately and allow organization/client name to be optional, with a backfill and a new Drizzle migration only after the baseline repair is complete. Test both new and edited entries.
4. Canonicalize work days using `WORK_SCHEDULE_DAY_OPTIONS` at save and display boundaries. Render previously saved out-of-order arrays in weekday order without changing their meaning. Test out-of-order clicks and reload.

**Acceptance:** education can save one valid entry with an untouched second row; date 31 is selectable after month navigation; self-employed work is expressible without pretending to have an employer; selected days always display in weekday order.

### 4. Improve profile and recommendation guidance (P2)

1. Distinguish an incomplete-profile zero-results state from a complete-profile/no-open-jobs state using `hasPersonalization` and profile completion. Give new seekers clear links to add profile details, skills/preferences, and a resume; keep an accurate empty-jobs message for complete profiles.
2. Decide whether resume is optional or required for the “Strong” label. Recommended: keep upload optional, show it as a separate recommended step, and explain the current completion score. If product chooses a resume-dependent strength label, update the calculation and its tests together.

**Acceptance:** a new seeker sees next steps, a complete seeker with zero matches sees an honest no-results message, and profile strength copy accurately explains the resume’s role.

## Release gates

Add backend contract/integration tests for editable profile payloads, file validation/statuses, verification retry, and preserving existing user intent.
- Run authenticated Playwright flows in Chromium and WebKit or an available supported browser against an isolated migrated test database. Cover 600px and mobile viewports, legal pages, date navigation, scrollbar interaction, self-employed entries, and signup/login/verification paths. Mock or use a test provider for Google OAuth.
- Run frontend and backend type-check/lint, targeted tests, and a safe end-to-end smoke after the database repair. Review any new schema migration against its ledger and snapshot before applying it. Roll out server/client contract changes together and retain correlation IDs to diagnose remaining 400/500 responses.
